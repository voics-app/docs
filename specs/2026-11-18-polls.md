# Persistent polls

Status: proposed contract and implementation slice for [messages#14](https://github.com/discordy-voics/messages/issues/14). [ADR0029](../adr/0029-persistent-polls.md) explains storage, ordering and operations. This document does not mark the issue delivered or enable the feature.

## Create and display

`POST /channels/{channel_id}/messages` accepts an optional `poll` with `question.text` (1–300 Unicode scalar values), 2–10 `answers` with `poll_media.text` (1–55), optional Unicode `poll_media.emoji.name`, `duration` in whole hours (1–768, default 24), `allow_multiselect` (default false) and `layout_type` (1 only). Answer IDs are assigned 1 through N by the server; clients cannot choose them. Whitespace-only question/answer text, custom emoji IDs and unknown poll fields fail validation. Emoji are optional decoration; this initial slice supports Unicode only and does not silently accept unverified custom-guild emoji.

A poll can accompany normal content or a reply and can be the only message content. Existing attachment, TTS and mention rules still apply. Polls cannot be forwarded, placed in a scheduled draft, created by the internal webhook/interaction path, or attached to a system message. Message edits cannot change or remove the poll definition; ordinary content edits do not reset its votes or expiry. Poll question/answers are rendered as text and do not trigger mentions or embeds.

Creation requires fresh VIEW_CHANNEL, SEND_MESSAGES (SEND_MESSAGES_IN_THREADS in a thread), SEND_POLLS, and any applicable attachment/TTS permissions. Public bot creation uses these same checks. Standard DMs, group DMs and guild text/thread channels use the same model. Ephemeral/P2P return 409/50160 and must not send question, answers or votes to this store. The client leaves server polls unavailable in private modes.

`Message.poll` contains immutable question/answers, an absolute RFC3339 `expiry`, multiselect/layout and optional `results`. Absent results are unknown; never show invented zeros or clear a newer cache. `results` contains `version`, `is_finalized` and a complete count for every answer. `me_voted` and `vote_version` are omitted from public broadcasts when the viewer is unknown. Finalized polls remain readable while their message exists.

## Read, vote and end

| Operation | Route | Success |
|---|---|---|
| Read your authoritative snapshot | GET `/channels/{channel_id}/polls/{message_id}` | 200 PollSnapshot, including results and viewer vote version |
| Select an answer | PUT `/channels/{channel_id}/polls/{message_id}/answers/{answer_id}/@me` | 200 PollSnapshot |
| Retract an answer | DELETE `/channels/{channel_id}/polls/{message_id}/answers/{answer_id}/@me?expected_vote_version=N` | 200 PollSnapshot |
| End your poll early | POST `/channels/{channel_id}/polls/{message_id}/expire` | 200 Message with finalized poll results |

PUT requires `{ "expected_vote_version": "N" }`; DELETE uses the equivalent required query parameter because DELETE bodies are poorly supported by intermediaries. Revisions start at `"0"` and are scoped to one poll and one authenticated voter. Single-choice PUT replaces a previous choice; multiple-choice PUT preserves other choices. No-op retries return the current snapshot without an increment. A stale version that would change the current choice returns 409/50035 with an `expected_vote_version` field error. Refresh before choosing again. Do not automatically overwrite a newer choice on a second device.

Reading/voting/expiry require fresh VIEW_CHANNEL and READ_MESSAGE_HISTORY on the current Standard channel. Voting is restricted to authenticated human user sessions; bot, webhook, interaction and application credentials cannot vote. SEND_POLLS is only needed to create; losing it does not remove an existing participant's readable poll. The author alone can end early; MANAGE_MESSAGES permits normal deletion, not impersonating the author to finalize a poll. A repeated author expiry returns the existing final result.

Unknown message/non-poll/deleted poll is 404. Invalid answer IDs/body are 400/50035. Missing access/permissions is 403. Closed or overdue vote mutations return 409/50035 with a `poll` field error; participant-cap exhaustion uses `poll.participants`. At the 100,000-participant cap, existing participants can still change/remove choices. Dependency/CAS retry exhaustion is 503 and does not imply a committed vote. A lost response can be reconciled with GET or an identical retry using the original expected version. Exact state is the authoritative snapshot, not the HTTP transport outcome.

## Live results and recovery

MESSAGE_POLL_VOTE_ADD and MESSAGE_POLL_VOTE_REMOVE contain channel/message/user IDs, optional guild ID, answer ID, the actor's complete `answer_ids`, actor `vote_version` and complete public `results`. A single-choice replacement emits REMOVE for the old answer and ADD for the new answer with the same final results/actor revision. Clients apply snapshots, never delta counts, so duplicates and either event order converge. Closing publishes MESSAGE_UPDATE with finalized poll results through the normal message stream.

Guild poll events use GUILD_MESSAGE_POLLS (bit 24); DM poll events use DIRECT_MESSAGE_POLLS (bit 25). User sessions already receive all intents. Message creation/update still follow existing message and MESSAGE_CONTENT filtering; a redacted message must not leak a question or answer text through `poll`. Vote payloads have no question/answer text. A bot without the poll intent receives no poll vote events.

On visible-poll entry, foreground and successful reconnect/resume, fetch GET for each visible poll with bounded concurrency. Merge by results version and per-viewer vote version, including an equal-results-version response that supplies previously missing viewer facts. Ignore older results, never reopen a finalized result from a delayed event, and never erase certified viewer facts from a public snapshot. A lost publication is repaired by that refresh. Optimistic selection is pending local UI state and cannot advance the certified revision.

The countdown disables new votes at `expiry`; `is_finalized` confirms the persisted tally. A vote admitted before the instant can race with finalization and be included; no new vote may be admitted once expiry is observed. Periodic finalization has a nominal 16-tick idle shard rotation with the documented defaults plus storage/backlog time. This is not a five-second production latency promise.

## Acceptance boundary

Backend acceptance requires the real-store, permission, HTTP-schema and expiry cases in ADR0029, plus create/history/edit/delete compatibility. Client acceptance needs desktop/mobile composer and rendered poll interaction, cross-device single/multi choice, early/automatic closing, forbidden/private states, duplicate/reordered events and reconnect repair. Gateway acceptance needs poll-intent routing and MESSAGE_CONTENT redaction. Keep these gates separate; a schema PR or backend test is not proof of the complete feature.
