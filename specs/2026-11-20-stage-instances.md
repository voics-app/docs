# Stage instances and voice enforcement

Status: draft implementation for [voice#9](https://github.com/discordy-voics/voice/issues/9). The stage metadata and voice publishing controls are separate slices; this document does not claim an end-to-end stage call is available.

A guild-only stage instance has an ID, guild and stage-channel IDs, and a topic. A member who can view the stage channel can fetch its active instance. A member with `MANAGE_CHANNELS` in that channel can start a stage, change its topic or end it. Starting twice for the same channel fails; the active channel key is unique in Postgres. The API commits each mutation and its `STAGE_INSTANCE_CREATE`, `STAGE_INSTANCE_UPDATE` or `STAGE_INSTANCE_DELETE` event in one transactional outbox operation. Gateway dispatch requires the `GUILDS` intent and channel visibility. Deleting the channel cascades its instance.

The desktop stage page exposes those metadata controls and refreshes on lifecycle dispatches. Stage audio is unavailable until enforcement is connected: the gateway refuses direct joins and moderator moves into stage channels, and desktop navigation does not start a voice connection. This prevents the current ordinary voice route from presenting a false audience mute.

The SFU draft can start with audio and video publishing separately disallowed, apply live permission changes, and refuse RTP for denied media. Signaling stores acknowledged permissions for SFU replay. Video covers camera and screen; another audio track such as soundboard must require both audio and its own soundboard permission. Compatibility defaults for old signaling are permissive, so they cannot be used as proof of stage protection during a mixed-version rollout.

Before enabling stage joins, gateway state must own `suppress` and `request_to_speak_timestamp`, authorize requests and moderator moves with channel permissions, and propagate each session's capabilities to its assigned signaling node over a trusted, node-specific control route. The route must authenticate the caller, order and acknowledge changes, and fail closed when authorization or connectivity is uncertain. Tokens, reconnect/replay, revocation, node migration and simultaneous commands need explicit tests. A public WebSocket URL is not a trusted internal control identity. Camera, screen and soundboard must not bypass audience suppression.

Acceptance remains open for the speakers/audience UI, hand raises and invitations, full voice enforcement and a two-client end-to-end call including revocation and reconnect. The metadata UI fixture test is not a live call. No production service, new server or deployment is part of this work.

## Proposed live capability contract (not yet enabled)

The gateway is authoritative for each voice session. A node-affine, authenticated update carries `session_id`, `node_id`, `registration_lease`, a monotonically increasing per-session `revision`, `expires_at` as Unix milliseconds, and explicit booleans `can_publish_audio`, `can_publish_video`, and `can_publish_soundboard`. Soundboard requires both audio and soundboard permission; audio, video and soundboard default to denied for stage sessions. Video covers camera and screen. A session cannot receive a grant from an older node registration or a request that was authorized for a different session.

Apply the whole capability object atomically in the SFU. Acknowledge only after application. Reject an older revision; a repeated revision is idempotent only when the complete contents match. Reject conflicting duplicates. A new grant must have a bounded, future expiry; the SFU converts the remaining duration to a monotonic deadline and independently denies publishing on expiry. Nodes require clock synchronization for the absolute expiry check, cap its duration, and never replay an expired grant after restart. Gateway renewals continue only while the authoritative permission remains valid. A failed acknowledgment, expired lease, lost control link or unknown session must not be interpreted as a successful grant; signaling closes or denies the session and reconciles state. A partition cannot deliver an immediate revoke: the SFU deadline bounds how long an already-issued grant can survive. Do not enable stage joins until that bound is chosen, implemented and tested.

The gateway must confirm a promotion only after the node applies it. For demotion it requests denial first; if acknowledgment is missing it treats the session as unsafe, disconnects where possible, and relies on the SFU deadline to end any partitioned grant. A restart, node migration or gateway reconnect starts denied until the current authoritative state is re-established. Existing permissive legacy defaults are not valid for stage sessions.

Required integration coverage uses real UDP peers and the actual control path: denied to granted to denied for audio, camera, screen and soundboard; soundboard-only grants must fail; stale revisions, mismatched node leases, conflicting duplicates, expiry, disconnect and replay must not restore old grants. Include simultaneous updates, a delayed acknowledgment, E2EE media and per-listener mute. Test both permission visibility and actual packet delivery rather than only UI state.

Voice WebSocket opcode 41, `PUBLISH_PERMISSIONS`, is proposed as a server-to-owner notification after SFU acknowledgment. It carries the session ID, revision, expiry and the three applied booleans. The client treats an absent, invalid, stale, expired or disconnected notification as denied. This notification is a UI gate only; the SFU remains responsible for packet enforcement.
