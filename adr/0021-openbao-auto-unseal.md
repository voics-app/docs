# 0021 — OpenBao auto-unseal with a static key

- Status: accepted
- Date: 2026-10-22
- Deciders: @oussamaelhajoui
- Technical story: [gitops#39](https://github.com/discordy-voics/gitops/issues/39)
- Related: [ADR 0006](0006-secrets-flow.md), [OpenBao unseal runbook](../runbooks/openbao-unseal.md)

## Context and Problem Statement

OpenBao was Shamir-sealed (5 shares, threshold 3, keys in DPAPI files on the owner PC). After every pod or node restart it stayed sealed until the owner ran `bootstrap/20-openbao.sh`. On 2026-10-22 `openbao-0` restarted and sat sealed for 13 hours: External Secrets could not refresh (`ClusterSecretStore` `InvalidProviderConfig`) and `secrets-sync` failed with 503. A single-node homelab must recover from a reboot without the owner at the PC.

## Decision Drivers

- Unattended recovery after a pod restart or VM reboot
- Free, no new always-on component on the single VM
- A realistic threat model: the cluster already holds the secrets OpenBao serves (ESO writes them into Kubernetes Secrets), so cluster-admin can read them anyway
- A path to something stronger when more nodes or a second VM exist

## Considered Options

1. **Static key seal** (`seal "static"`) with the key in a Kubernetes Secret.
2. **Transit seal** against a second small OpenBao on another VM.
3. **Cloud KMS** (AWS KMS, GCP KMS, Azure Key Vault).
4. Stay on Shamir and only add an alert.

## Decision Outcome

Chosen option: **1 now, 2 as a follow-up** once the dev VM or the 3-node cluster exists.

- OpenBao runs with `seal "static" { current_key = "env://BAO_SEAL_KEY" }`. The key is 32 random bytes (base64) in the Secret `voics-system/openbao-seal-key`, injected as an environment variable. It is generated by `bootstrap/20-openbao.sh`, never committed, and copied to the owner key store as `<KEYSTORE_PREFIX> seal key` so a rebuilt cluster can restore the same Secret and read a restored data directory.
- The existing Shamir shares were migrated (`unseal -migrate`) and are now **recovery keys**, kept in the same key store items. They no longer unseal; they authorise `generate-root`, rekey and seal-config changes. This also removes the "root token cannot be regenerated" limitation of the Shamir setup.
- Monitoring: the `openbao-seal-check` CronJob pushes `openbao_sealed` / `openbao_reachable` to VictoriaMetrics every 2 minutes and posts to an optional webhook; the ops portal shows the live seal state.

### Trade-offs, stated plainly

- Anyone with cluster-admin (or read access to Secrets in `voics-system`, or the node's disk) can read the seal key and, with a copy of the data directory, decrypt OpenBao. Shamir kept that power off the node. This is accepted: cluster-admin can already read every synced Kubernetes Secret, and the VM disk holds the Raft/pebble data and the Secret together.
- The seal protects **backups and stolen data directories** only as long as the key is not stored next to them. Keep `openbao-data` backups apart from the seal key (the key store on the owner PC, not the backup bucket).
- Rotating the key needs `previous_key` for one restart (runbook).

### Why not the others

| Option | Verdict |
|---|---|
| Transit seal on a second OpenBao | Stronger (the key leaves the node) but needs a second always-on instance that must itself be unsealed, i.e. the same problem one level up, and another VM. Revisit with the dev VM or three nodes. |
| Cloud KMS | Costs money, needs an internet dependency at every boot and a credential on the node that is as sensitive as the static key. |
| Shamir plus alert only | Alerts do not recover the service while the owner is away. |

## Consequences

- Reboots no longer need the owner. Verified on production: a deleted pod came back unsealed and the `ClusterSecretStore` stayed `Valid` ([runbook](../runbooks/openbao-unseal.md#restart-test-2026-10-22)).
- `bootstrap/20-openbao.sh` creates the Secret first, initialises with recovery keys, and finishes a Shamir migration if it finds one. `SEAL_MODE=static` is the default for `gen-serv` and `dev` (`clusters/*/env.conf`).
- Disaster recovery now needs two owner-held items: the recovery keys and the seal key.
- Follow-up: transit seal against a second OpenBao ([gitops backlog](https://github.com/discordy-voics/gitops/issues)).
